# Respuestas - Trabajo Práctico Comparable y Comparator

**Pregunta 1: ¿Por qué `Collections.sort()` no compila cuando le pasamos una `List<Estudiante>`? ¿Qué contrato exige Java que nuestra clase no está cumpliendo?**
`Collections.sort()` no compila porque el método genérico exige que los elementos de la lista implementen la interfaz `Comparable<? super T>`. Java requiere este contrato para establecer una relación de orden total entre los objetos; sin la implementación del método `compareTo()`, el compilador carece de una semántica de comparación que le permita determinar la precedencia posicional entre dos instancias de la clase `Estudiante`.

**Pregunta 2: ¿Por qué elegiste el atributo `promedio` como orden natural? ¿Qué pasaría si mañana un nuevo requisito pide ordenar por `cantidadMateriasAprobadas`? ¿Modificarías `compareTo`? ¿Qué consecuencias tendría?**
Se seleccionó el `promedio` por ser el atributo primario de mérito académico en el contexto universitario. Si existiese un nuevo requerimiento para ordenar por `cantidadMateriasAprobadas`, modificar el método `compareTo` afectaría a todas las partes del sistema que dependan implícitamente de este ordenamiento previo. Alterar el orden natural altera el comportamiento global de colecciones como `TreeSet` o `TreeMap` que operan con dicha clase, violando así la estabilidad del sistema.

**Pregunta 3: `Comparable` nos ata a un único criterio de ordenamiento. ¿Qué problemas de diseño introduce esto si nuestro sistema necesitara ordenar la misma lista de estudiantes de 4 formas distintas según el contexto? Relacioná tu respuesta con los principios de responsabilidad única (SRP) y abierto/cerrado (OCP).**
Implementar múltiples lógicas condicionales dentro de `compareTo()` violaría el Principio de Responsabilidad Única (SRP), ya que la entidad de dominio asumiría el control de reglas de presentación de la capa de negocio. Adicionalmente, violaría el Principio Abierto/Cerrado (OCP), debido a que cada nuevo criterio de ordenamiento requeriría la modificación del código fuente de la clase `Estudiante`. Las entidades de dominio deben estar cerradas a la modificación de criterios de ordenamiento específicos del contexto.

**Pregunta 4: Explicá con tus palabras qué es un overflow de enteros, por qué el "truco de la resta" lo provoca, qué parte del contrato de `Comparator` rompe, y por qué `Integer.compare()` no sufre este problema.**

Un *overflow* (desbordamiento) ocurre cuando el resultado de una operación aritmética excede la capacidad máxima de almacenamiento en memoria para un tipo de dato primitivo, en este caso los 32 bits de un `int` (rango de -2,147,483,648 a 2,147,483,647). 
El "truco de la resta" (`a - b`) provoca overflow cuando se intenta evaluar distancias entre extremos del espectro numérico, como restar un valor negativo a un entero positivo máximo (ej: `2147483647 - (-1)`). A nivel de hardware, esto envuelve la representación en complemento a dos y genera un número negativo (-2147483648).
Esto rompe el contrato de **transitividad y asimetría** de la interfaz `Comparator`. El método indicará erróneamente que el número mayor es menor que el número negativo (devolverá `< 0`), corrompiendo por completo el algoritmo de ordenamiento interno (como Timsort).
`Integer.compare(x, y)` no sufre de este problema porque no evalúa distancias aritméticas reales, sino que opera con lógica condicional pura bajo el capó (`return (x < y) ? -1 : ((x == y) ? 0 : 1);`), garantizando seguridad y precisión independientemente de los valores involucrados.

**Pregunta 5: ¿Qué patrón de diseño estás aplicando al usar un `Map<String, Comparator<T>>` en lugar de un `switch`? Explicá cómo se relaciona este patrón con el polimorfismo y por qué es preferible a la alternativa procedural.**
Se está aplicando el **Patrón Strategy**. En lugar de tener una única clase o método con múltiples bloques condicionales (arquitectura procedural), se define una familia de algoritmos (`Comparator<Estudiante>`), se encapsula cada uno y se los hace intercambiables en tiempo de ejecución. 

El diccionario (`Map`) actúa como un registro de estrategias. Esto se apoya directamente en el polimorfismo: el servicio invoca `.sort(comparador)` sin saber qué implementación subyacente de `Comparator` está ejecutando (resolución dinámica de métodos). 

Es preferible a la alternativa procedural porque respeta estrictamente el principio Open/Closed (OCP). Si en el futuro se requiere agregar el criterio `sortBy=fechaIngreso`, no es necesario modificar ni el Service ni el Controller; simplemente se inyecta una nueva entrada en el `Map` en el momento de la construcción. Las estructuras `switch` o `if-else` acoplan el código y obligan a modificar la clase central por cada nuevo requerimiento funcional, elevando el riesgo de introducir bugs de regresión.
